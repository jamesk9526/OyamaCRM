PATH A / STATIC FILES

Publish this website.

  1. Preview the folder.

    From the repository root, run this local preview command, then open http://localhost:8082.

    python -m http.server 8082 --bind 127.0.0.1 --directory website/v2

  2. Upload the website contents.

    Copy the contents of website/v2/ into your static host’s document root or publish directory. Include all four HTML pages, the CSS/JS files, and the entire assets folder. No install or build command is needed.

  3. Configure the entry point.

    Serve index.html at your site root. Keep docs.html, hosting.html, and screenshots.html reachable directly. Relative asset links also support publishing under a subdirectory. No single-page-app fallback is required.

  4. Connect your domain.

    Use your host’s domain and HTTPS configuration. Once DNS resolves, verify the homepage, direct documentation links, screenshots, and mobile navigation over HTTPS.

Publish only website/v2/. The repository root contains application code and configuration that do not belong in a public static document root. Python’s server is for local preview.

Prepare the CRM environment.

The repository’s deployment template targets an Ubuntu VPS with a reverse proxy and PM2. Plan for a compatible Node.js runtime, pnpm 10, MySQL, protected persistent storage, and a domain with HTTPS.

CONFIGURE BEFORE BUILDING

Make configuration explicit.

Create a protected production environment file based on .env.example. Replace example secrets and stale version metadata. Do not publish or commit the populated file.

ConfigurationPurpose
DATABASE_URLProduction MySQL connection with appropriate application access
JWT_SECRETStrong, private authentication secret
CREDENTIAL_ENCRYPTION_KEYPersistent encryption key for configured credentials; preserve with protected backups
FRONTEND_ORIGINExact HTTPS browser origin allowed by the API
NEXT_PUBLIC_APP_URLPublic HTTPS app URL
NEXT_PUBLIC_API_URLPublic API base URL for the deployment’s routing
PORT / API_PORTWeb and API listening ports
SMTP and optional integrationsConfigure only enabled workflows and verify credentials separately

NEXT_PUBLIC_* values are browser-visible and can be baked into the web build. Never put secrets in them. Export the production environment before migrations, generation, builds, and process startup; the API’s dotenv loader does not automatically select .env.production.

BUILD & RELEASE

Prepare a controlled release.

Use an authorized checkout of the intended revision. Back up the database and persistent files before applying migrations, and verify that you can restore them. This Bash sequence assumes a protected, shell-compatible .env.production file.

set -euo pipefail
set -a
source .env.production
set +a
pnpm install --frozen-lockfile
pnpm db:generate
pnpm typecheck
pnpm lint
pnpm test:unit
pnpm test:api
pnpm build
pnpm build:server
# Apply reviewed migrations in your release window.
pnpm db:migrate
# Start only the donor web and API services.
pnpm exec pm2 start ecosystem.config.cjs --only oyama-crm-web,oyama-crm-api --env production --update-env

For an existing installation, restart the selected existing processes with the updated environment after a successful build. Run pnpm exec pm2 save after verifying the process list, and configure your server’s PM2 startup integration for reboot persistence.

Adding the separate Letters workspace

If enabled, run pnpm build:letters, configure its API origin and reverse-proxy routing, and start oyama-letters explicitly. Do not start unrelated services simply because they appear in the ecosystem file.

This is a repository-based deployment guide, not a claim that a fresh production deployment has been exercised. Review the production-readiness checklist and validate your actual environment before onboarding staff.
ROUTING & HTTPS

Connect the public URL to the services.

The existing VPS template routes web traffic to port 3650 and API traffic to port 4000. Preserve the /api prefix when proxying to Express, and forward host and HTTPS information. Review any web-owned API routes and optional workspace routing for your enabled features.

Keep upstream services and the database off the public internet where possible. Terminate HTTPS at your proxy, use the exact production origin, and leave permissive development CORS disabled.

OPERATE WITH CONFIDENCE

Verify the release. Keep it healthy.

  • Check PM2 process state and logs; verify the web URL and /api/health.
  • Sign in using the intended staff role and verify permissions with a restricted account.
  • Check constituents, donations, fiscal period selection, and a representative report.
  • Validate enabled email, letters, uploads, and public links in a controlled test.
  • Monitor application errors, storage, database availability, and backups.
  • Keep the previous release and a tested recovery plan; schema rollback may require database recovery rather than only reverting code.
